# Prototype Talk

Use this Skill to make an interactive, evidence-linked explanation beside a prototype. The primary complete path is a **local runnable Web source Demo plus PRD/Mock**. React JSX/TSX and HTML/JavaScript are supported; Vue SFC parsing is not yet supported. Figma Design, published Figma Sites and Axure links supply partial evidence and require the [link workflow](references/link-inputs.md). A link recognized by `doctor` is not itself a generated explanation.

## Run in stages

1. **Preflight and input snapshot.** Run `node scripts/doctor.mjs --source <absolute-demo-directory>` (or `--link <URL>`). Confirm the runnable entry, build freshness and PRD/Mock inclusion. For a PRD URL, actually read it and save a versioned, citable Markdown snapshot under `docs/requirements/`; a URL string alone is not indexed. Report missing inputs and unsupported components. A missing Codex CLI only disables the optional CLI mode, not this Skill. Never call a preflight result a completed review.
2. **Choose interpretation and authorize once, then start.** After preflight, check optional CLI availability with `doctor.mjs --check-cli`. If this project and concrete input scope have no prior authorization for the chosen model destination, proactively ask **one combined question before model interpretation**. Offer (a) current conversation model, with cards generated while this chat runs; (b) Codex CLI, if available, with automatic processing after this chat ends; (c) local index only, with no new model cards. Spell out that the selected model may receive relevant source, PRD, Mock and future operation records, including input changes and before/after page states. Each model option must explicitly authorize that scope and name its destination; local-only is a decline of model processing. Do not infer consent from a mode label or from starting a local server. Reuse an authorization already given for the same project, destination and scope in this conversation, and do not ask again on every run. Read the [mode and consent details](references/conversation-model.md). For current conversation mode, start `node scripts/server.mjs --source <absolute-demo-directory> --port <free-port>` and process its queue in this chat. For authorized CLI mode, use `--cli-model`, passing `--model-authorized` only for the first explicitly authorized run. For local-only, use `--index-only` and clearly report that no new full explanation will be generated. Open the **printed Prototype Talk URL**, preserving the Demo path, query and hash. The scanner builds a candidate graph from controls, handlers, routes or state changes, destination regions, and source display fields. Preserve conditions and unresolved edges; do not present source candidates as executed behavior.
   Run one writing server per source project and review directory; several ports against the same `docs/prototype-talk/` can overwrite one another's in-memory review state. If the Skill's server or matching code changes during a review, restart that existing server on its current port and reload the browser before judging the result. A running Node process keeps its previously imported code, and an older tab can keep an older overlay script. Verify the port and source directory of the page the reviewer actually has open.
3. **Runtime region and evidence package.** Record which page, dialog, section or field an action actually targets. A new page or tab uses the whole destination page, a dialog uses its whole dialog, and a field selection uses that field. Identify the clicked control with the shared layered anchor in `assets/anchor-core.js`: logical page → named dialog/tab/form/section → repeated row or item → control label and stable attributes. The browser overlay and local store use the same matcher. Ignore generated IDs such as `react-aria…`; never attach a card when candidates tie or a saved row/region conflicts. Preserve an ambiguous operation as pending location. The control anchor identifies where the click occurred; the observed destination region determines how much of the page its explanation covers. Compare that region and its visible fields with the source graph; retain both on mismatch rather than overwriting one. For each logical screen, function or operation, collect only relevant source lines, PRD requirements, Mock/data read-write clues, and actual traces. Treat query-driven React screens as separate logical pages. Keep source, documented requirements, observed behavior and user-confirmed rules distinct. A matching label is a candidate link, not proof of data flow. Missing evidence stays explicit.
4. **Model interpretation.** Generate the entry-page brief first; group related logical screens into one batch. In conversation mode, claim and submit pending jobs during this active chat using the linked handoff; do not leave the initial page empty merely because the queue exists. Generate an operation card when opened or explicitly requested, using scoped evidence. After the chat ends, browser actions persist as pending jobs until the next Skill invocation. A pending or failed task has an honest visible state and a targeted retry. The model uses the same source/runtime region graph for the **product result** as well as the technical fields: explain the trigger, target page/dialog/section, actual visible change, conditions and acceptance result in short facts. A field count is not a product outcome. If a known target was merely reselected, say that the page stayed in place. The model produces product explanation, technical candidates and focused questions; it must not invent production APIs, infer unseen business results or overwrite human-confirmed rules. Classify PRD/Demo differences as factual discrepancies, missing operation evidence as test gaps, and absent formal services as technical gaps. A discrepancy is shown directly with both sides' evidence; do not turn it into a product choice question.
5. **Three-way review and program validation.** Compare PRD requirements separately with source behavior and runtime observation; label each discrepancy with its two origins. Check output schema, current source snapshot, reference locations and origin types. For submit operations, check whether cited code has validation and write branches, then require corresponding failure and success outcomes and a data effect; flag branch-sensitive citations that do not show the claimed branch. These checks find omissions but do not establish full semantic correctness. Keep claims pending until the product or technical reviewer confirms them. Present Product, Technical, Evidence and Review Todo views beside the original interaction. A reviewer can supplement/correct each fact; save versioned rules in `docs/prototype-talk/` and regenerate documents from that state. Formal API contracts require technical confirmation.
6. **Report completion.** Report pages/operations with current cards, queued or failed jobs, unresolved evidence, and the model timing from `node scripts/metrics.mjs --state <demo>/docs/prototype-talk/review-state.json`. A returned card is available for review, not confirmed. Distinguish first usable card time from full completion time.

The local program owns scanning, data indexing, tracing, evidence locations, validation, state and document rendering. Only interpretation and optional semantic dispute review need model calls. A separate reviewer model is **not** the default production path until the frozen-case comparison in the [evaluation protocol](references/evaluation.md) shows a net benefit.

Read [detailed workflow and review rules](references/detailed-workflow.md) only for the relevant implementation or review question. The component vocabulary in `scripts/component-catalog.mjs` selects component-specific review questions; it does not identify a rendered instance. Shared anchor matching lives in `assets/anchor-core.js`; the bundled `assets/finder.js` may make a temporary CSS selector for the current interaction, but that selector never becomes a saved operation identity. Neither `esbuild` nor an npm install is needed to run the Skill or a bundled viewer. Model output contracts live in `scripts/*.schema.json`, and executable behavior in `scripts/` and `assets/`. Do not treat the detailed reference as another step to replay on every call.
